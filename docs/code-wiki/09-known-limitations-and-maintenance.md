# 已知限制、风险与维护建议

[返回索引](./README.md)

## 1. 当前事实边界

| 主题 | 当前事实 | 不应误述为 |
| --- | --- | --- |
| 数据库 | SQLite + 文件混合持久化 | PostgreSQL/RLS/分布式数据库 |
| 架构 | 单机模块化单体、双进程 | 微服务或可水平扩展集群 |
| 前端 | 原生大型脚本 | React/TypeScript 组件化应用 |
| 权限 | 固定三角色 + 功能开关 + owner map | 动态 RBAC、组织层级和部门租户 |
| 更新 | 同 Schema Manifest v2 更新 | 任意数据库迁移或跨版本自动升级 |
| Runtime | Windows portable lifecycle | Linux/Kubernetes 生产编排 |
| 测试 | 59 个 Python 测试文件；收敛分支增加最小 GitHub Actions | CI 通过即可替代生产验收 |
| `2026.09.4` | 独立发布标签 | 已合并 `main` 或永久 Production Baseline |

## 2. 主要技术债

### 超大 `main.py`

路由、文件存储、Provider 协议、队列和业务规则共处一文件，影响可测试性和故障隔离。建议按领域逐步抽取 service/adapter，不做一次性重写；每次抽取保持 API 和旧前端行为不变。

### 超大前端脚本

普通画布和智能画布各自维护复杂全局状态，存在重复的媒体、任务、保存和 Provider 逻辑。建议先建立可重复的浏览器场景，再抽取无副作用工具和 API client；禁止以“重构”为由改变旧视觉/交互。

### 企业隔离是覆盖层

Upstream 仍能直接读写共享文件，权限依赖 Gateway 拦截与 owner map。一旦 Upstream 被直接暴露，隔离会被绕过。所有部署必须保持 Upstream loopback-only，并对新增路由做请求、响应、事件三面审查。

### SQLite 并发上限

SQLite 适合当前单机范围，但高并发写、跨进程长事务和多节点共享不是其目标。若业务升级到数百人高并发，迁移 PostgreSQL 应作为独立数据工程，不能只替换连接字符串。

### 文件与数据库一致性

业务对象在文件系统，归属在 SQLite，无法天然形成一个 ACID 事务。中断可能产生“文件已写但归属未写”或相反状态。新增关键写入应设计可重放回执、幂等修复和对账流程。

## 3. 发布线分叉风险

本次核验仍有三个不同基线：`origin/main`、主线收敛分支、`2026.09.4` 标签。收敛分支已经移植现场有效代码，但 PR 合并前分叉仍存在。维护时必须：

1. 先确定修复目标是主线、客户精确版本还是发布候选。
2. 用 commit/tree/manifest 标识，不只写“最新版”。
3. 将跨分支移植作为独立 cherry-pick/integration 工作并重新测试。
4. 不把现场运行证据自动外推到另一提交。

## 4. 在线更新缺口

- 数据库 migration/restore 尚未接入 Update Center。
- Release 必须具备完整三件套，源码 ZIP 不能替代。
- 网络代理与 GitHub 可达性可能使在线更新失败，需要保留离线升级兜底。
- 管理后台能打开不表示具备 `system_update` 权限。
- 更新成功还需验证重启、健康、数据、配置和素材，而非只看 pointer 已切换。

## 5. 安全缺口与注意事项

- Gateway 没有内建公网 TLS、WAF 或企业 SSO。
- JWT 是 Cookie 会话，不是多 IdP 身份关联模型。
- 固定角色不是细粒度组织权限；目前没有部门 API Key/费用归属模型。
- Provider/CLI 调用继承本机网络与进程环境，应避免把秘密写入日志和诊断。
- 强审计覆盖安全治理，但普通业务写入不都具备同等级不可变审计。
- 开发配置允许宽松模式；正式环境必须启用严格安全并更换占位秘密。

## 6. 测试证据边界

仓库测试能证明代码契约，但不能自动证明：

- 客户机器上的杀毒软件、代理、文件 ACL 和长路径兼容。
- 正式签名安装器在干净 Windows 上通过。
- 外部 AI Provider 的实时可用性与计费正确。
- 七天/长稳运行结果适用于另一 commit。
- 数据库迁移已经在真实生产数据上演练。

每份验收应记录 commit/tree、Release ID、Runtime identity、测试主机、命令和原始结果。

## 7. 推荐演进顺序

1. 先保持旧前端体验与现有 API 兼容，补齐自动保存、任务回执和故障注入。
2. 把 Provider 调用抽到明确 adapter，并统一超时、代理、幂等与未知结果。
3. 逐域抽离 `main.py`，建立服务边界和运行时 schema 校验。
4. 把文件/SQLite 跨存储写入变成可恢复 workflow。
5. 在真实并发与容量数据支持下，决定 PostgreSQL、对象存储和任务队列迁移。
6. 再设计组织/部门、SSO、费用归属、MCP/Agent 委托等企业能力。

这是一条风险排序，不表示上述后续能力已经批准或实现。

## 8. Wiki 维护规则

- 每次合并影响架构的提交，更新首页基线和相关章节。
- 新模块加入 `02-repository-map.md`，关键公开类/函数加入 `03-backend-reference.md`。
- 新外部系统必须写明凭据、网络、超时、重试与失败语义。
- 新数据表同步更新数据字典与迁移状态。
- 新正式入口同步更新运行命令；历史聊天命令不作为文档事实源。
- 计划、候选、已实现、仓库验证、物理主机验证和生产通过必须使用不同措辞。
