# 升级恢复核验与解除阻断

适用范围：更新作业已进入 `RECOVERY_REQUIRED`，且运维人员已通过独立恢复操作，让一个可信的 Release 和数据库重新正常运行。此流程只核验并解除后续升级阻断；它不修复数据库、不切换版本，也不重新提交未完成的 AI 任务。

## 操作顺序

1. 暂停新的升级操作，保留原作业目录、备份、诊断 ZIP 和现场记录。先独立核对当前 Release、业务数据、备份和未完成任务；不确定时继续阻断，不点击解除。
2. 使用已启用 `system_update` 权限的超级管理员进入管理后台“更新中心”。选择待恢复的 Job ID，点击“核验并查看证据”。
3. 系统重新核验：作业与计划一致、没有并行升级锁、当前指针属于原源版本或目标版本、Manifest 与已落盘文件一致、SQLite 完整性/外键/模式匹配、正式 Runtime 健康检查通过。任一不符即拒绝解除。
4. 对照页面报告和独立现场记录，输入当前 Release ID、12–500 字不含密钥的人工核验记录，以及当前账号密码。确认时系统再次运行全部核验；报告指纹变化即拒绝。
5. 成功后，系统先写不可变核验文件和必须成功的安全审计记录，再写作业事件，最后将状态置为 `RECOVERY_CLEARED`。任何前置写入失败，作业仍处于 `RECOVERY_REQUIRED`，后续准备/执行升级继续被拒绝。保留 Job ID、核验文件 SHA-256 和安全审计事件用于追溯。

## 不得把解除阻断当作恢复

- 如果当前服务无法启动、数据库模式与 Release 不匹配、数据库完整性检查失败，先单独恢复并重新核验；不要伪造状态文件、清除锁文件或编辑 `current-release.json` 来绕过保护。
- 若数据库已被迁移到不确定状态，必须用经核验的备份和对应版本恢复，并对照画布、素材与未完成任务。此功能不会自动恢复备份，也不保证任务费用对账。
- `RECOVERY_CLEARED` 是某次作业的终态，不是新版本发布或客户设备验收通过。发布与在线升级仍需分别验证 Release 资产、源版本兼容和升级/失败恢复路径。

## 兼容性限制

已发布的 `2026.09.4` 更新器只接收与源版本完全相同的数据库模式，不能直接接收含新表或数据库迁移的主线构建。新的在线 Release 必须先在源版本上通过 Manifest/Inventory/ZIP 三件套校验及一次实际源→目标升级演练；不能只给现有主线改版本号后发布。
