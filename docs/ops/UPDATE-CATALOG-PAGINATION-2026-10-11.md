## 问题与实现

原 GitHub v1/v2 Provider 各自只请求最近 50 个 Release。历史桥接或指定目标位于后续页面时可能不可见；若简单串接部分页面，网络失败、目录发布竞争或恶意分页地址会让不完整列表冒充完整事实。

- `release_catalog.py` 共用目录读取：固定企业仓库，构造每页可信 URL，不直接跟随服务器 URL。GitHub 实际 Link 使用 numeric repository 路径；已通过真实仓库 API 核实并绑定 `1255587052`，只接受本项目的名称/数字 ID 两种形态。每页 50 条，最多 1000 条；21 页包含恰好 1000 条时必要的空终止页。短页附 next 时继续，满页缺 Link 时仍探测下一页。超限、不明响应、非法 next、跨仓库/跨源/跳页、重定向和页面内重复身份拒绝，不返回“最近一部分”。
- 多页读取后重新核验首页面；跨页重复身份或首页面变化时整次重读一次，持续变化则拒绝。这是有边界的分页一致性保护，不宣称 GitHub 具有事务快照。最终准备阶段仍核对当前安装、源数据库、路线、Manifest、inventory 和 archive。
- `SafeHttpClient.read_json_response` 增加有界状态/ETag/Link 返回；304 必须绑定同一仓库/凭据/页的已核验缓存与合法 validator。不匹配 validator、无缓存 304、206 或非 JSON 不能被当作成功。原资产下载/read_bytes 不接受 304，超限、超时及重定向凭据保护保持原契约。
- 全部页面成功后一起替换临时缓存。每次读取都向 GitHub 条件核验全部页面；网络/权限失败不能退回旧缓存。缓存仅存元数据与 validator，仓库和凭据指纹隔离，最多 4 个上下文；不落盘、不保存凭据、不引入 TTL/自动保留政策。
- v1/v2 共用上述目录，保留原 draft、开发通道、完整资产和仓库绑定筛选。API 返回目录完整性摘要，未完整读取时返回固定中文错误，不停服务、不创建升级暂存。
- 不可变路线预览缓存按凭据、发布身份、通道、路线 SHA、URL/大小绑定，最多 1000 项。先成功核验新目录，才可使用；只影响页面建议。prepare/execute 仍重新读取和核验声明，不以缓存作为执行授权。
- 更新页面加载目录时禁止选择旧目标启动新的准备；失败清空候选并显示固定中文“未启动升级”。请求序号防止迟到旧成功/旧失败覆盖新结果。已验证 READY 作业沿用自己的执行权限，不因另一次目录查询失败而取消。

分页/API 契约依据：[GitHub List releases](https://docs.github.com/en/rest/releases/releases#list-releases)、[分页](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) 及 [条件请求](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests-if-appropriate)。本包保持既有 API version，不夹带协议版本迁移。

最终关联回归 161 passed、9.61 秒（JUnit 计时，含 17 项文档契约和 APP_ROOT 写入审计），XML 为 `t/C4a/alias-final-tests.xml`。覆盖真实 numeric repository 路径、同一仓库名称大小写以及字符串/整数相同身份的拒绝；HTTP 宣称长度与短正文不一致不能伪装成完整空目录。已知目录失败显示为固定中文提示，实际渲染与脚本验证通过。文档登记检查为 133 文档、11 权威、21 冻结、290 本地链接，无错误；没有完整企业套件或安装演练的手工重跑。
