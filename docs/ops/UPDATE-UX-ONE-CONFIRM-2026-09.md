# 管理后台一次确认更新体验

超级管理员进入“更新中心”后，页面自动检查固定 GitHub 仓库的完整正式版和开发版 Release，列出高于当前运行版本的目标，默认选择最新正式版。开发版使用 GitHub prerelease 标记，页面明确显示“开发版”及风险；draft、资产不完整的版本不列出。同一版本号不能同时复用于开发版和正式版，转正时须发布更高的版本号。管理员选定目标、输入当前账号密码并确认一次后，页面依次调用既有准备与执行接口；准备仍完成完整资产校验、不可变物化和数据库兼容性检查，执行仍使用独立 handoff、数据备份/迁移（适用时）、启动健康检查及失败恢复。UI 简化不放宽任何后端门禁。

每轮完成功能或修复后可直接发布对应版本，但“发布”不等于跳过验证：仍须有完整三资产、版本与源版本兼容说明、定向测试和升级/失败恢复证据。开发版可以更快发布给自愿试用者，不得标为正式版；正式版须满足既定交付验收。检查接口原有的 `latest` / `update_available` 保持“最新正式版”的语义，新客户端使用 `releases` 选择正式版或开发版。当前已实现的选择入口在管理后台网页；独立桌面客户端的更新入口尚未交付，后续应复用同一检查、准备和执行接口，不另建一套更新器。仅允许向更高版本升级，不提供任意降级；数据库变更时尤其不能把版本选择当作回滚手段。

进度窗口只展示真实作业状态：下载校验、受控停机、数据库迁移、重启、健康检查、成功、回退或人工恢复。下载接口尚未提供逐字节进度，故不显示虚假百分比。准备请求返回作业 ID 前应保持页面打开；ID 落盘后可从本会话存储恢复查询，服务重启期间的连接错误只提示等待，不会再次提交升级。

此变更只改善已具备能力的版本，不使旧 `2026.09.4` 更新器自动支持主线新数据库。客户现装版本须先接收独立构建、同 Schema、完整三资产的兼容更新；发布前仍需源版本安装副本的真实升级/失败回退演练。
