## 5. 2026-10-11 长期容量目标与架构约束补充

CAPACITY-2026-10-11（CONFIRMED）：来源为负责人本次明确补充；这是长期设计约束，不是新的 BR、B/N 或场景编号，不改变原 14 BR、37 项映射及 104 条候选场景。记录可以在后续适合的正式文档维护中纳入主线；记录、文档合并、实现、容量实测及客户验收分别判断。

### 5.1 设计目标，不是现有承载能力

未来 1—2 年面向单企业客户 **500 名以上员工、峰值 200 名以上员工同时活跃创作** 设计。员工总数、同时活跃用户、在途 AI 请求及同时执行的付费生成请求不是同一指标；不要求同时执行 200 个付费请求，不声称当前系统已达到这一容量。

保留模块化单体、Windows 单机版、SQLite 和现有客户升级路径。未来中大型企业服务器版根据实际负载逐步演进到 PostgreSQL、独立 AI Worker、受管理资产存储及多实例部署；两种部署形态尽可能共用业务领域模型、服务端权限规则及 API 契约，不建立两套独立企业业务系统。不要求当前部署 PostgreSQL、Redis、微服务或多节点集群。

### 5.2 随核心工作包一并落实的约束

进入已获对应实施授权的 B13/B14/B15/B16/B17、N29/N34/N37 工作包时，将以下要求与原业务目标一起实现及验收，不拆成大量微型架构任务：

- 任务受理、执行尝试、供应商回执、异常恢复与费用对账形成持久事实，不仅依赖单个进程内存。
- 部门、项目、业务任务、AI 请求、资产及版本具有稳定身份。
- 多人并发修改具有事务与版本冲突保护，画布或正式资产不得被无提示覆盖；正式资产版本不覆盖的现有约束继续有效。
- 数据库访问经清晰的 Repository 或等效数据访问边界，减少未来迁移 PostgreSQL 对业务代码的影响。
- 大型素材通过稳定资源身份与 Storage Adapter 管理，避免业务逻辑深度绑定本机绝对路径。
- 权限由服务端统一执行，不依赖页面隐藏或信任客户端传入的用户标识。
- 任务执行、数据库写入、素材读写、WebSocket 和 API 逐步具备容量监控与压力验证能力。
- 新 Schema、任务状态及资产格式须考虑现有客户升级、数据兼容及失败恢复；新增容量方向不豁免既有交付门禁。

### 5.3 容量验证与本轮授权边界

后续适合的工作包采用建议的 100、200、300 名同时活跃用户混合操作阶梯，分别观察 AI 执行、画布保存、数据库写入、素材读写及实时连接。具体硬件、负载组合和可承载能力须由真实或合成负载证据确定；这些人数不是已经通过的测试，也不为本轮阶段 3 新增容量门禁。发现瓶颈后先依据证据定位，再选择数据库、Worker、缓存、文件存储或服务部署优化，不预设一次引入全部分布式组件。

本次只确认长期方向及约束：继续现行路线图阶段 3 的安装、修复、升级恢复、缓存清理和保留数据卸载/重装；不因容量补充中断或重建已验收基础，也不改动 #151 的独立审查范围。没有新增业务代码、大规模架构重构、生产数据库切换、生产操作或 Release 授权；DEC-011—DEC-021 中仍待确认的政策不因此生效。不创建第二份路线图，不修改历史规划原文、原需求 ZIP、冻结报告或原场景编号。

执行节奏仍按完整工程工作包自主推进、集中验证和交付；本补充不人为限定开发及排障时长，不重复已充分证明的事实。开发设备无法操控的外部测试主机不作为必须亲自操作的任务；不可验证的门禁明确登记，不虚报通过。

## 6. 2026-10-11 专业服务器与云端生产部署定位补充

SERVER-DEPLOYMENT-2026-10-11（CONFIRMED）：来源为负责人开发交接中的明确补充。专业企业服务器、私有化服务器和主流云服务器的长期生产运行是正式产品目标；Windows 本地部署是其中一种交付形态，不能作为唯一长期运行平台。本记录不新增 BR、B/N 或验收场景编号，不复制路线图，不将目标写为现有能力。

两类部署尽可能复用同一业务领域模型、API、服务端权限和资源身份；当前保留模块化单体、Windows 安装维护、SQLite、本地文件与 Runtime Supervisor。服务器环境优先评估 Linux 兼容性，查明真实 Python/Windows 依赖与必要改造，再在适合的正式工作包内建立配置外置、无交互启停、服务管理、健康检查、日志、权限/网络边界和可重复交付。当前未完成 Linux 安装器、容器化或云端生产发布。

容量增强按实测瓶颈逐步采用 PostgreSQL、独立 Worker、受管理文件/对象存储、缓存/传输优化及多实例协调；后台任务不能长期只依赖单个 Web 进程内存。高可用、冗余、备份、故障切换及灾难恢复按业务可靠性目标演进，不要求当前引入微服务、Docker、Kubernetes 或 Redis。RPO/RTO、基础设施预算、云供应商和部署拓扑仍需负责人确认。

Windows 特有的 Registry、Job Object、KnownFolder、固定入口和桌面交互保留在适配层；跨平台业务与运行/数据恢复契约不能新增固定盘符或 Windows 桌面前置。新 Schema、任务状态和资产格式继续携带已部署客户的升级与失败恢复方案，不因容量或平台演进绕过门禁。

公网生产验收须包含 TLS/HTTPS、反向代理信任、认证授权、网络隔离、访问与请求限制、身份/密钥保护和审计。共享 SaaS 多租户、每客户独立部署或混合方式尚未决定；已有部门 Owner 隔离不等于跨企业租户隔离。

继续现行阶段 3 的 C2 独立审查以及保留数据卸载/重装工程；本补充不授权正式 Release、生产设备操作、破坏性客户迁移或大规模重构。治理助手独立审查/常规合并审批和负责人正式发行/生产审批的职责边界不变。

## 7. 2026-10-13 长期供应商适配与临时兼容边界

PROVIDER-ADAPTATION-2026-10-13（CONFIRMED）：负责人明确要求项目负责长期接入供应商（例如 Zhenzhen）的模型调用适配，不能把常规请求契约维护转交给管理员或普通创作用户。普通用户继续在现有 API 节点选择模型及创作参数；无需独立请求模板页面或配置步骤。
