2026-10-20：#182与安装简化#183已按批准合入main0d0078f，准确main三项CI最终SUCCESS；正式v2026.10.4已发布并逐项回读，固定源码2859a2a。10.2 Setup完整升级/登记、10.3在线升级与目标失败恢复在开发机合成安装通过；公开10.3原更新服务确认direct、10.2确认requires_intermediate，现场由负责人操作待反馈，见[10.4发行记录](../ops/RELEASE-2026.10.4-RECORD.md)。当前仍在4.2：下一完整包先收集现场升级/数据保留反馈并定向修复实际阻断，同时澄清原JSON编辑未知请求及账号通道，再有界真实复测，禁止自动重提。4.3、RunningHub和云/多实例继续暂缓。


> 安全修复 → 数据升级能力 → **统一安装与在线升级体验** → 部门与可靠任务 → 资源缓存与桌面客户端 → PostgreSQL 及高可用 → 企业集成

这是一条交付依赖，不是必须完全串行的调研日程。测试、文档、日志、模块化及未来接口设计可随当前任务推进；未经升级/恢复验证的新业务表不能先推给客户。规模风险若提前出现，按实测调整并记录决定，不能机械等到“第六阶段”才考虑数据边界。

专业企业服务器和云服务器生产部署是正式产品目标，Windows 本地部署是其中一种形态；当前未验证 Linux/容器/云端生产支持。500 名以上员工、200 名以上峰值活跃创作及两类部署共用业务核心是长期设计约束，详见 [需求决策登记](../decisions/REQUIREMENTS-DECISION-REGISTER.md#6-2026-10-11-专业服务器与云端生产部署定位补充)。当前单台 Windows 主机继续交付；Linux、云部署及规模容量实施待负责人后续需求，当前只保持业务/平台边界与演进准备，不另建路线图、不启动整体重构。

最新完成/分支/发布状态只见 [CURRENT_PROJECT_STATUS](../CURRENT_PROJECT_STATUS.md)。阶段 3 部分实现，正式 10.1 已有测试与生产单设备升级成功反馈；通用维护基础、基线收口及生命周期诊断已经合并 main，但不包含所有历史适配器或完整安装维护闭环。一种正式固定入口的必要更新/恢复已随 #157 收口，准确 10.2 包的正式 10.1 v2 单跳与目标失败恢复通过；发行状态见 CURRENT。安装维护余项按实际需求补充，不阻塞下列可靠任务业务，不按每个应用版本复制工具。

PR #108 Runtime、#119 浏览器/路由边界已经合并，#111 已关闭；不是下一轮再做一次相同修复。

## 8. 阶段 6：PostgreSQL 与高可用

- 标准服务器运行在适合的既有工作包内逐步建立：优先评估 Linux 真实依赖，落实外置配置、无交互启停、健康/日志、服务管理与可重复交付；平台特有逻辑留在适配层。服务器兼容调查和业务接口边界可提前随当前阶段推进，不等于已部署。
- 长期保留 SQLite 单机；团队 PostgreSQL 采用相同领域服务和存储接口。接口边界在早期设计，不等到迁移才重写全部业务。
- SQLite → PostgreSQL 专门迁移向导、完整性/权限/费用校验和失败恢复；不夹带在普通应用更新。
- 基于写入等待、队列积压、延迟、存储与恢复指标决定容量，不按“几十/几百用户”宣称能力。
- 后续以 100/200/300 活跃用户的混合负载验证画布、AI 受理/查询、素材与实时连接；活跃用户数不等于同时付费请求数。按瓶颈扩容，不预设微服务、Docker、Kubernetes 或 Redis 为前置目标。
- 团队任务领取、幂等、并发/连接池/索引、共享素材存储、多 Worker 和故障恢复有专项验证。
- Redis 只按明确需要引入；多节点升级、排空与 PostgreSQL 备份/PITR 不复用单机文件回退假设。
- 在扩展生产规模前确定 RPO/RTO、备份保留与灾备证据；真实容量风险可提前触发专项设计评审。

验收：单节点退出不丢受理任务，并发权限/费用一致；迁移和多节点升级/灾备各有可重现证据。

## 9. 阶段 7：企业集成
