# 客户 2026.09.5 数据升级过渡版

状态：开发中；不是正式 Release，不得发给客户安装。

## 起点与目的

- 唯一已核对的客户源 Release：`ice-2026.09.5-7609bb1b7cfa`。
- 该版本的更新器只接受 `same-schema-no-migration` 和 `code-release-pointer`，数据库快照 SHA-256 为 `6b4a1deca34b5724217db868d1b8015f222982fddf63e952fb73e8d2966900c4`。
- 第一跳只安装新更新器与迁移原语；不得新增表、登记元数据、修改客户数据库或移动 `data`、`config`、素材目录。
- 后续业务表版本必须另行证明旧数据库的备份、版本登记、迁移、目标健康校验及失败恢复；目前不能把第一跳称为“已经具备客户数据迁移能力”。

## 已落地的第一跳约束

过渡版 Release 构建器仍生成与 09.5 完全相同的旧数据库证据。新增的 `versioned.py` 是程序代码，不计入旧式 `migration_ids`；否则 09.5 更新器会误判数据库迁移清单变化并拒绝升级。新版更新器识别无版本记录的旧证据时，仅允许目标证据逐字节对应同一 Schema，并只读核验当前数据库的表结构、完整性和外键；任何不符均阻断。它不会在准备或切换中偷偷为旧数据库创建版本表。

## 下一道发布门槛

1. 在客户 09.5 的准确发布包、源版本指针及有代表性的旧数据库副本上，完成第一跳完整三资产预检、切换、重启和失败回退。无需另设干净 Windows 设备门禁。
2. 为第二跳实现明确的“旧 Schema 登记”作业：先做可验证的一致性备份，再在事务中登记版本记录并应用已声明的迁移；失败时恢复数据库与代码指针。当前主线的版本化迁移函数要求源数据库已有版本记录，**不能直接用于客户 09.5 数据库**。
3. 注入备份失败、迁移中断、目标启动失败、恢复失败和进程中断；只有代码、数据库与运行健康均可证明恢复时才报告回退成功，否则进入 `RECOVERY_REQUIRED` 并禁止自动重试。
4. 首个真正改变数据库结构的 Release 必须另列其准确源版本、目标 Schema、迁移清单、业务数据保留断言和恢复证据。不能仅因第一跳成功就发布新增业务表。

## 验证边界

当前已从 GitHub 正式 `2026.09.5` Release 下载并验证完整三资产（Manifest、Inventory、30 MB 归档），且成功物化为只读核对副本；归档与 Manifest 校验通过。针对代码，已验证由真实初始化器生成、含模拟客户记录的旧库，其结构与正式 09.5 快照一致，过渡计划前后数据库字节不变。针对未来版本化数据库，补上失败恢复时按版本指纹而非旧库对象清单核验的定向测试。

尚未生成过渡版正式三资产，也尚未在客户安装副本或客户设备执行第一跳；当前没有真实客户数据库副本，模拟记录不能替代客户数据验收。尤其尚未实现带备份的旧库版本登记及第二跳迁移，故本分支仍不得发布给客户。客户现有 09.5 不受此开发分支影响。
