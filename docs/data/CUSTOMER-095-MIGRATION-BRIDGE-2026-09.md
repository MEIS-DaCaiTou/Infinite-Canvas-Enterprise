# 客户 2026.09.5 数据升级过渡版

状态：迁移/回退代码与 09.5 隔离副本演练已完成；不是正式 Release，不得发给客户安装。

## 起点与目的

- 唯一已核对的客户源 Release：`ice-2026.09.5-7609bb1b7cfa`。
- 该版本的更新器只接受 `same-schema-no-migration` 和 `code-release-pointer`，数据库快照 SHA-256 为 `6b4a1deca34b5724217db868d1b8015f222982fddf63e952fb73e8d2966900c4`。
- 第一跳只安装新更新器与迁移原语；不得新增表、登记元数据、修改客户数据库或移动 `data`、`config`、素材目录。
- 后续业务表版本必须另行证明旧数据库的备份、版本登记、迁移、目标健康校验及失败恢复；第一跳仍必须严格保持同 Schema，不在客户库上提前登记版本。

## 已落地的第一跳约束

过渡版 Release 构建器仍生成与 09.5 完全相同的旧数据库证据。新增的 `versioned.py` 是程序代码，不计入旧式 `migration_ids`；否则 09.5 更新器会误判数据库迁移清单变化并拒绝升级。新版更新器识别无版本记录的旧证据时，仅允许目标证据逐字节对应同一 Schema，并只读核验当前数据库的表结构、完整性和外键；任何不符均阻断。它不会在准备或切换中偷偷为旧数据库创建版本表。

## 下一道发布门槛

1. 在客户 09.5 的准确发布包、源版本指针及有代表性的旧数据库副本上，完成第一跳完整三资产预检、切换、重启和失败回退。无需另设干净 Windows 设备门禁。
2. 第二跳已新增旧 Schema 登记作业：Release 证据必须同时绑定准确旧 Schema 指纹和只读预演所得的登记后指纹；受控停机后由 SQLite 收敛 WAL，校验无活动连接，生成并核验一致性备份，然后在同一事务中登记版本记录与执行声明的迁移。备份之前不修改业务 Schema。目标版本启动或健康检查失败时，先恢复数据库再恢复版本指针与旧服务。
3. 已注入备份失败、迁移校验失败、目标启动失败、目标健康失败、恢复失败以及提交后结果不明。仅当代码、数据库与运行健康均可证明恢复时报告 `ROLLED_BACK`；恢复不确定时进入 `RECOVERY_REQUIRED`，不自动重试。仍需在正式候选包上验证进程中断后的人工恢复流程。
4. 首个真正改变数据库结构的 Release 必须另列其准确源版本、目标 Schema、迁移清单、业务数据保留断言和恢复证据。不能仅因第一跳成功就发布新增业务表。

## 验证边界

已从 GitHub 正式 `2026.09.5` Release 下载并验证完整三资产（Manifest、Inventory、30 MB 归档），且成功物化。使用该正式 Release 的完整文件复制出两份隔离安装目录，并由发布包内的 Python 与 09.5 初始化器创建旧库，加入模拟用户与画布归属记录，另外创建模拟配置和素材。目标 Release 和启动器使用测试桩，执行真实更新中心的数据库迁移及版本指针写入：成功路径保留数据并登记到版本 2，健康失败路径恢复到无版本记录的旧库和 09.5 指针；两条演练均通过。单元/更新中心定向测试覆盖备份、迁移、回退和失败阻断。测试入口 `ICE_095_RELEASE_ROOT=<已核验的09.5物化目录> py -3.11 -m pytest enterprise/tests/test_customer_095_clone_drill.py -q`。

演练发现正式 09.5 数据库采用 WAL：只读核验可能留下 `-wal/-shm`，最初阻断备份。因此迁移器在已停机的数据库上用 SQLite checkpoint 收敛 WAL；若仍有活动连接或旁路文件，不删除文件、不强行迁移，直接阻断。迁移提交后重新收敛并计算完整主库哈希，防止仅哈希主文件却遗漏 WAL 中的新 Schema。

尚未生成第一跳过渡版的正式三资产，也未用该三资产在 09.5 安装副本上演练实际在线下载、启动和失败回退；上述第二跳使用测试目标，并不证明新 Release 已可发布。当前没有真实客户数据库副本，模拟记录不能替代客户数据验收。`DEFAULT_MIGRATIONS` 仍为空，尚未指定任何真实业务表迁移、目标 Schema 或可交付版本。正式发布前还需构建并核验第一跳及第二跳的准确 Release、核验旧更新器接收第一跳、运行真实启动健康检查、复核中断恢复审计。客户现有 09.5 不受此开发分支影响。
